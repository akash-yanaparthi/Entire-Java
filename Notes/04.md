# Java Architecture — What Happens Behind the Scenes?

Now that we understand Java, variables, methods, classes, and objects, let's understand the most important question:

> **What actually happens behind the scenes when we run a Java program?**

To understand this, we need to look at the complete Java architecture.

---

# 1. The Complete Picture

When we write a Java program and run it, there are several stages involved:

```text
             Java Source Code
                 (.java)
                    │
                    ↓
             Java Compiler
                (javac)
                    │
                    ↓
              Bytecode
                 (.class)
                    │
                    ↓
             Class Loader
                    │
                    ↓
           Bytecode Verification
                    │
                    ↓
           JVM Runtime Memory
                    │
                    ↓
             Execution Engine
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
       Interpreter           JIT
          │                   │
          └─────────┬─────────┘
                    ↓
             Machine Code
                    ↓
                   CPU
                    ↓
                 Output
```

Let's understand every part.

---

# 2. Step 1 — We Write Java Code

First, the programmer writes Java source code.

Example:

```java
public class Main {

    public static void main(String[] args) {

        int a = 10;
        int b = 20;

        int result = a + b;

        System.out.println(result);
    }
}
```

This code is saved in a file:

```text
Main.java
```

At this stage, this is just **Java source code**.

The CPU cannot directly execute this Java source code.

---

# 3. Step 2 — Java Compiler

The Java compiler is called:

```text
javac
```

We compile the program using:

```bash
javac Main.java
```

The compiler analyzes the Java source code.

It checks things such as:

* Syntax
* Data types
* Variable declarations
* Method declarations
* Class structure
* Other compile-time rules

If the code is valid, the compiler generates **bytecode**.

```text
Main.java
   │
   ↓
javac
   │
   ↓
Main.class
```

The `.class` file contains Java **bytecode**.

---

# 4. What Is Bytecode?

Bytecode is an intermediate representation of the Java program.

It is not the original Java source code.

It is also not CPU-specific machine code.

For example:

```text
Java Source Code
       ↓
    Compiler
       ↓
    Bytecode
```

The important idea is:

> **The Java compiler converts source code into bytecode, and the JVM executes that bytecode.**

This bytecode is one of the major reasons Java can achieve platform independence.

---

# 5. Why Can't the CPU Directly Execute Bytecode?

A CPU understands **machine instructions specific to its architecture**.

For example, different CPUs can have different instruction sets.

Bytecode is designed for the JVM rather than for a specific physical CPU.

So we have:

```text
Java Code
    ↓
Bytecode
    ↓
JVM
    ↓
Machine Code
    ↓
CPU
```

The JVM acts as the layer between Java bytecode and the underlying operating system/hardware.

---

# 6. Step 3 — Running the Program

After compilation, we can run the program:

```bash
java Main
```

The `java` command starts a JVM and asks it to launch the `Main` class.

Conceptually:

```text
java Main
   ↓
JVM starts
   ↓
Main class is loaded
   ↓
main() method is located
   ↓
Program begins execution
```

---

# 7. Step 4 — Class Loader

When the JVM starts executing a Java program, it needs to load the required classes.

This is the job of the **Class Loader subsystem**.

For example:

```text
Main.class
   ↓
Class Loader
   ↓
JVM
```

The Class Loader loads class definitions into the JVM.

Java programs can depend on many classes:

```text
Main
 ├── Student
 ├── String
 ├── System
 └── Other classes
```

The JVM loads the classes that are needed during execution.

---

# 8. Class Loading

Class loading is not simply:

```text
.class → JVM
```

There are important stages involved.

A simplified view is:

```text
Loading
   ↓
Linking
   ├── Verification
   ├── Preparation
   └── Resolution
   ↓
Initialization
```

Let's understand them.

---

# 9. Loading

The **Loading** phase finds the binary representation of a class and creates a corresponding class representation inside the JVM.

For example:

```text
Main.class
   ↓
Class Loader
   ↓
Class information loaded into JVM
```

---

# 10. Linking

After loading, the class is linked.

Linking includes:

```text
Verification
Preparation
Resolution
```

## Verification

The JVM verifies that the loaded bytecode is structurally valid and satisfies JVM constraints.

This helps prevent invalid bytecode from being executed.

Conceptually:

```text
Bytecode
   ↓
Verification
   ↓
Valid?
   ↓
Continue
```

## Preparation

The JVM prepares memory for class-level/static data and assigns default values where applicable.

For example:

```java
static int count = 10;
```

The class initialization step is responsible for executing the initialization code that assigns the actual value.

## Resolution

Symbolic references in the class can be resolved to concrete runtime references.

Resolution may happen lazily, when needed.

---

# 11. Initialization

During initialization, the JVM executes class initialization logic.

For example:

```java
class Test {

    static int number = 10;

    static {
        System.out.println("Class initialized");
    }
}
```

When the class is initialized, its static initialization code is executed according to Java's initialization rules.

---

# 12. Runtime Data Areas

Once the JVM is running, it needs memory to store different kinds of information.

The JVM specification defines several **runtime data areas**.

A simplified view is:

```text
JVM Runtime Data Areas
│
├── Heap
├── Method Area
├── Java Virtual Machine Stacks
├── PC Registers
└── Native Method Stacks
```

Let's understand each one.

---

# 13. Heap

The **heap** is the runtime memory area where objects and arrays are allocated.

For example:

```java
Student student = new Student();
```

The `new` expression creates a `Student` object.

Conceptually:

```text
new Student()
      ↓
   Object
      ↓
    Heap
```

The reference variable `student` refers to that object.

```text
Stack                     Heap

student ───────────────→ Student object
                           name
                           age
```

The exact implementation details depend on the JVM.

---

# 14. Stack

Each thread has its own **JVM stack**.

When a method is called, a new **stack frame** is created for that method invocation.

For example:

```java
public static void main(String[] args) {

    int a = 10;

    calculate();
}

static void calculate() {

    int x = 20;
}
```

Conceptually:

```text
JVM Stack

┌──────────────────┐
│ calculate()      │
│ x = 20           │
├──────────────────┤
│ main()           │
│ a = 10           │
├──────────────────┤
│ ...              │
└──────────────────┘
```

When `calculate()` finishes, its stack frame is removed.

---

# 15. Stack vs Heap

This is a very important Java concept.

### Stack

Generally contains information associated with method execution, including:

* Stack frames
* Local variables
* Operand stacks
* References used by method execution

### Heap

Generally contains:

* Objects
* Arrays

For example:

```java
Student student = new Student();
```

Conceptually:

```text
Stack                         Heap
─────                         ────

student ───────────────────→  Student Object
                              name
                              age
```

The reference variable and the object are not the same thing.

---

# 16. PC Register

Every JVM thread has its own **Program Counter (PC) register**.

It keeps track of the current JVM instruction being executed by that thread.

Conceptually:

```text
Instruction 1
Instruction 2
Instruction 3 ← PC
Instruction 4
Instruction 5
```

It helps the JVM know where execution should continue.

---

# 17. Native Method Stack

Java can interact with code written in native languages such as C or C++ through mechanisms such as the Java Native Interface (JNI).

The JVM provides a native method stack for execution of native methods, where applicable.

---

# 18. Execution Engine

Now we reach one of the most important parts of the JVM:

> **Execution Engine**

The Execution Engine is responsible for executing the bytecode.

A simplified view is:

```text
Bytecode
   ↓
Execution Engine
   ├── Interpreter
   └── JIT Compiler
```

---

# 19. Interpreter

The **Interpreter** executes bytecode instructions.

Conceptually:

```text
Bytecode
   ↓
Interpreter
   ↓
Execute instructions
```

This can allow a program to start executing quickly because the JVM does not necessarily need to compile the entire application into native machine code before execution begins.

However, repeatedly interpreting frequently executed code can be less efficient than executing optimized native code.

---

# 20. JIT Compiler

JIT stands for:

> **Just-In-Time Compiler**

The JIT compiler can compile frequently executed bytecode into native machine code at runtime.

Conceptually:

```text
Bytecode
   ↓
Frequently executed code
   ↓
JIT Compiler
   ↓
Native Machine Code
   ↓
CPU
```

This allows the JVM to optimize code based on information collected while the application is running.

---

# 21. Interpreter + JIT

A simplified execution model is:

```text
              Bytecode
                  │
                  ↓
             JVM Execution
              /         \
             ↓           ↓
      Interpreter       JIT
             │           │
             │           ↓
             │      Native Code
             │           │
             └─────┬─────┘
                   ↓
                  CPU
```

The exact execution strategy depends on the JVM implementation and runtime behavior.

---

# 22. Garbage Collector

Java provides **automatic memory management**.

When objects are no longer reachable by the running program, they can eventually be reclaimed by the **Garbage Collector (GC)**.

For example:

```java
Student student = new Student();

student = null;
```

After `student` is set to `null`, the previously referenced object may become unreachable, assuming there are no other references to it.

Conceptually:

```text
Student Object
      ↑
      │
   student
      │
      ↓
    null
```

The object may now be eligible for garbage collection.

> **Important:** Garbage collection is automatic, but you should not assume that an object is collected immediately after becoming unreachable.

---

# 23. Putting Everything Together

Let's take a simple program:

```java
public class Main {

    public static void main(String[] args) {

        int a = 10;
        int b = 20;

        int result = a + b;

        System.out.println(result);
    }
}
```

Now let's follow what happens.

### Step 1 — Write Code

```text
Main.java
```

The programmer writes Java source code.

### Step 2 — Compile

```bash
javac Main.java
```

The compiler generates:

```text
Main.class
```

### Step 3 — Run

```bash
java Main
```

The JVM starts.

### Step 4 — Load

The Class Loader loads the required class definitions.

### Step 5 — Verify and Link

The JVM verifies and links the classes as required.

### Step 6 — Initialize

Class initialization occurs according to Java's rules.

### Step 7 — Find `main()`

The JVM starts execution from the application's `main` method.

```java
public static void main(String[] args)
```

### Step 8 — Create Stack Frame

A stack frame is created for the `main()` method.

```text
JVM Stack

main()
 ├── a = 10
 ├── b = 20
 └── result = 30
```

### Step 9 — Execute Bytecode

The Execution Engine executes the generated bytecode.

The JVM may interpret it and/or compile frequently executed code using the JIT compiler.

### Step 10 — CPU Executes Machine Instructions

Eventually, native machine instructions are executed by the underlying processor.

```text
Java Code
   ↓
Bytecode
   ↓
JVM
   ↓
Execution Engine
   ↓
Native Machine Code
   ↓
CPU
```

### Step 11 — Output

The program produces:

```text
30
```

# 25. Where Does the Operating System Fit?

The JVM itself runs as a program on the operating system.

So the overall architecture can be viewed as:

```text
┌─────────────────────────────┐
│       Java Application      │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│             JVM             │
│                             │
│ Class Loader                │
│ Runtime Data Areas          │
│ Execution Engine            │
│ Garbage Collector           │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│       Operating System      │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│          Hardware           │
│             CPU             │
│            Memory           │
└─────────────────────────────┘
```

This is why we say:

> **The JVM is platform-dependent, while Java bytecode is designed to be platform-independent.**

A Windows JVM is built to work with Windows, while a Linux JVM is built to work with Linux.

The same Java bytecode can therefore be executed by JVM implementations for different platforms.

---

# 26. JDK, JRE, and JVM

These terms are often confused.

A simplified conceptual relationship is:

```text
JDK
 │
 ├── Development Tools
 │      ├── javac
 │      ├── java
 │      └── Other tools
 │
 └── Runtime Components
        └── JVM
```

Historically, the JRE was commonly described as:

```text
JRE
 ├── JVM
 └── Runtime Libraries
```

And conceptually:

```text
JDK
 ↓
JRE
 ↓
JVM
```

However, modern Java distributions do not generally package a separate standalone JRE in the same way older Java versions did.

The important distinction is:

```text
JDK → Used for Java development
JVM → Executes Java bytecode
```

# 28. Key Takeaways

* `.java` contains **Java source code**.
* `javac` compiles Java source code.
* `.class` contains **JVM bytecode**.
* The JVM loads and executes bytecode.
* The Class Loader loads class definitions.
* The JVM verifies and links classes before/while they are prepared for execution.
* The JVM has runtime data areas such as the heap, JVM stacks, PC registers, method area, and native method stacks.
* Objects and arrays are allocated in the heap.
* Method execution uses stack frames in thread-specific JVM stacks.
* The Execution Engine executes bytecode.
* The Interpreter can execute bytecode.
* The JIT compiler can compile frequently executed code into native machine code.
* The Garbage Collector automatically manages reclaiming memory for unreachable objects.
* The operating system runs the JVM.
* The CPU ultimately executes machine instructions.
* Java's **WORA (Write Once, Run Anywhere)** idea comes from using platform-specific JVM implementations to execute the same bytecode.

## One-Line Summary

> **Java source code is compiled into bytecode, the JVM loads and manages that bytecode, the execution engine interprets and/or JIT-compiles it into native instructions, and the CPU executes those instructions.**
