# Access Specifiers in Java

Access specifiers, also called access modifiers, control the visibility and accessibility of classes, variables, methods, constructors, and other members in Java.

Java provides four access levels:

1. `public`
2. `protected`
3. Default / package-private
4. `private`

The main purpose of access specifiers is to control who can access a particular class or class member.

---

# 1. public

The `public` access modifier provides the widest access.

A `public` member can be accessed from:

- The same class
- The same package
- A different package
- A subclass in another package
- Any other class, provided the class itself is accessible

Example:

    class Student {

        public int age;

        public void study() {
            System.out.println("Student is studying");
        }
    }

Another class can access them:

    class Test {

        public static void main(String[] args) {

            Student s = new Student();

            s.age = 20;
            s.study();
        }
    }

Here, both `age` and `study()` are public, so they can be accessed from another class.

---

# 2. private

The `private` access modifier provides the most restricted access.

A `private` member can be accessed only inside the same class.

Example:

    class BankAccount {

        private double balance;

        private void calculateInterest() {
            System.out.println("Calculating interest");
        }
    }

Another class cannot directly access them:

    class Test {

        public static void main(String[] args) {

            BankAccount account = new BankAccount();

            // account.balance = 1000;       // Error
            // account.calculateInterest(); // Error
        }
    }

The `private` modifier is commonly used for instance variables to achieve encapsulation.

---

# 3. protected

The `protected` access modifier provides access within:

- The same class
- The same package
- Subclasses in different packages

Example:

    class Parent {

        protected int value = 10;
    }

A subclass can access it:

    class Child extends Parent {

        void show() {
            System.out.println(value);
        }
    }

`protected` is especially useful in inheritance.

---

# 4. Default / Package-Private

If no access modifier is specified, Java uses default access.

Example:

    class Student {

        int age;

        void study() {
            System.out.println("Studying");
        }
    }

Here, `age` and `study()` have package-private access.

They can be accessed by classes in the same package.

They cannot normally be accessed directly by classes in a different package.

Example:

    class Student {

        int age;
    }

Another class in the same package:

    class Test {

        void display() {

            Student s = new Student();

            s.age = 20;
        }
    }

This is allowed because both classes are in the same package.

---

# Access Specifier Comparison

| Access Modifier | Same Class | Same Package | Subclass in Different Package | Different Package |
|---|---:|---:|---:|---:|
| `private` | Yes | No | No | No |
| Default | Yes | Yes | No | No |
| `protected` | Yes | Yes | Yes | No* |
| `public` | Yes | Yes | Yes | Yes |

`protected` access in a different package is available through inheritance, subject to Java's access rules.

# Simple Memory Trick

Think of access levels from most restrictive to least restrictive:

    private
       ↓
    default
       ↓
    protected
       ↓
    public

Or:

    private → Same class
    default → Same package
    protected → Same package + subclasses
    public → Everywhere

# Why Should Variables Usually Be private?

Variables represent the internal state of an object.

For example:

    class BankAccount {

        public double balance;
    }

This allows outside code to directly modify the balance:

    BankAccount account = new BankAccount();

    account.balance = -500000;

This is dangerous because the class has no control over how its data is modified.

Instead, we normally make the variable private:

    class BankAccount {

        private double balance;

        public void deposit(double amount) {

            if (amount > 0) {
                balance += amount;
            }
        }

        public double getBalance() {
            return balance;
        }
    }

Now outside code cannot directly modify `balance`.

Instead, it must use the methods provided by the class.

---

# Why Variables Should Be private

Making variables private provides:

- Data protection
- Controlled modification
- Validation
- Encapsulation
- Better maintainability
- Reduced coupling
- Ability to change internal implementation without affecting outside code

---

# Example: Without Encapsulation

    class Student {

        public int marks;
    }

Now:

    Student s = new Student();

    s.marks = -100;

The class cannot prevent invalid values.

---

# Example: With Encapsulation

    class Student {

        private int marks;

        public void setMarks(int marks) {

            if (marks >= 0 && marks <= 100) {
                this.marks = marks;
            }
        }

        public int getMarks() {
            return marks;
        }
    }

Now:

    Student s = new Student();

    s.setMarks(85);

The class controls how `marks` is modified.

Invalid values can be rejected.

---

# Why Should Methods Usually Be public?

Methods represent the operations or behavior that an object provides to the outside world.

For example:

    class BankAccount {

        private double balance;

        public void deposit(double amount) {

            if (amount > 0) {
                balance += amount;
            }
        }

        public double getBalance() {
            return balance;
        }
    }

The variable `balance` is private.

But the methods `deposit()` and `getBalance()` are public.

This creates a controlled interface through which other classes can interact with the object.

For example:

    BankAccount account = new BankAccount();

    account.deposit(1000);

    System.out.println(account.getBalance());

The outside code does not need to know how `balance` is internally stored or how the deposit operation is implemented.

---

# Important Clarification

It is NOT a Java rule that:

> "Methods should always be public."

Methods do not always need to be public.

The correct principle is:

> Make members as restrictive as possible while still allowing the required design.

A method should be `public` when it is part of the class's external API and needs to be called by other classes.

A method should be `private` when it is an internal helper method that should not be exposed outside the class.

Example:

    class BankAccount {

        private double balance;

        public void deposit(double amount) {

            validateAmount(amount);

            balance += amount;
        }

        private void validateAmount(double amount) {

            if (amount <= 0) {
                throw new IllegalArgumentException("Invalid amount");
            }
        }
    }

Here:

    deposit()

is public because it is an operation that outside code needs to use.

But:

    validateAmount()

is private because it is an internal implementation detail.

---

# Why Not Make Every Method public?

Suppose we write:

    class BankAccount {

        public void deposit(double amount) {
            validateAmount(amount);
            updateBalance(amount);
        }

        public void validateAmount(double amount) {
            // ...
        }

        public void updateBalance(double amount) {
            // ...
        }
    }

Now outside code can directly call:

    account.validateAmount(1000);
    account.updateBalance(1000);

These methods may not be intended for external use.

Making everything public:

- Exposes unnecessary implementation details
- Increases coupling
- Makes the class harder to change
- Increases the number of ways other classes can interact with the class
- Makes the public API larger than necessary

Therefore, methods should not automatically be public.

---

# Public Methods and Private Variables

A common Java design pattern is:

    private variables
           ↓
    public methods
           ↓
    controlled access

Example:

    class Employee {

        private double salary;

        public void setSalary(double salary) {

            if (salary >= 0) {
                this.salary = salary;
            }
        }

        public double getSalary() {
            return salary;
        }
    }

Outside code interacts with:

    setSalary()
    getSalary()

but cannot directly access:

    salary

This is encapsulation.

---

# Why Use Getters and Setters?

Getters and setters provide controlled access to private variables.

Example:

    class Employee {

        private String name;

        public String getName() {
            return name;
        }

        public void setName(String name) {
            this.name = name;
        }
    }

Usage:

    Employee e = new Employee();

    e.setName("John");

    System.out.println(e.getName());

Here:

    getName()

reads the value.

    setName()

changes the value.

---

# Getters and Setters Are Not Always Required

A private variable does not automatically require both a getter and a setter.

For example:

    class BankAccount {

        private double balance;

        public double getBalance() {
            return balance;
        }
    }

There is no setter.

This means outside code can read the balance but cannot directly change it.

The class controls how the balance changes:

    public void deposit(double amount) {

        if (amount > 0) {
            balance += amount;
        }
    }

This is often better than providing:

    public void setBalance(double balance)

because arbitrary modification of the balance may not be desirable.

---

# Read-Only Property

A private variable with only a getter can provide read-only access.

Example:

    class Student {

        private final int rollNumber;

        public Student(int rollNumber) {
            this.rollNumber = rollNumber;
        }

        public int getRollNumber() {
            return rollNumber;
        }
    }

Outside code can read:

    student.getRollNumber();

but cannot directly change the value.

---

# Write-Only Concept

A class can also expose an operation that accepts data without providing a getter.

For example:

    class PasswordManager {

        private String password;

        public void setPassword(String password) {
            this.password = password;
        }
    }

There is no public getter for the password.

This prevents other classes from directly retrieving the stored value through the class API.

---

# Encapsulation and Access Specifiers

Encapsulation is closely connected to access modifiers.

A common design is:

    class BankAccount {

        private double balance;

        public void deposit(double amount) {

            if (amount > 0) {
                balance += amount;
            }
        }

        public double getBalance() {
            return balance;
        }
    }

Here:

    private
       ↓
    Protect internal state

    public methods
       ↓
    Provide controlled access

This is one of the most common examples of encapsulation in Java.

---

# Public Does Not Mean "Better"

`public` provides maximum accessibility.

That does not mean it should always be preferred.

For example:

    public int balance;

exposes the internal state directly.

Whereas:

    private int balance;

provides stronger control.

The correct design principle is:

> Use the least accessible modifier that satisfies the requirement.

For example:

    private
    ↓
    package-private
    ↓
    protected
    ↓
    public

Choose the narrowest appropriate access level.

---

# Access Modifier and Encapsulation

Consider:

    class Employee {

        private double salary;

        public void increaseSalary(double amount) {

            if (amount > 0) {
                salary += amount;
            }
        }

        public double getSalary() {
            return salary;
        }
    }

The outside world does not directly manipulate:

    salary

Instead, it requests an operation:

    increaseSalary()

The class controls how its internal state changes.

This is a major benefit of encapsulation.

---

# Internal Helper Methods

Not every method is part of the public API.

Example:

    class Order {

        public void placeOrder() {

            validateOrder();
            calculateTotal();
            saveOrder();
        }

        private void validateOrder() {
            System.out.println("Validating order");
        }

        private void calculateTotal() {
            System.out.println("Calculating total");
        }

        private void saveOrder() {
            System.out.println("Saving order");
        }
    }

Here:

    placeOrder()

is public.

The other methods are private implementation details.

Outside code only needs:

    order.placeOrder();

It does not need to know how the order is validated, calculated, or saved.

---

# Public API vs Internal Implementation

A useful mental model is:

    Class
      │
      ├── Public API
      │      ↓
      │   Used by outside code
      │
      └── Private implementation
             ↓
          Used internally

Example:

    class Car {

        public void start() {
            checkFuel();
            startEngine();
        }

        private void checkFuel() {
            System.out.println("Checking fuel");
        }

        private void startEngine() {
            System.out.println("Starting engine");
        }
    }

Outside code:

    Car car = new Car();

    car.start();

Outside code does not need to call:

    car.checkFuel();
    car.startEngine();

because those are implementation details.

---

# Can a Class Be private?

A top-level class cannot normally be declared `private`.

For example:

    private class Student {
    }

is invalid for a top-level class.

A top-level class can generally be:

    public class Student {
    }

or package-private:

    class Student {
    }

However, a nested class can be private:

    class Outer {

        private class Inner {
        }
    }

---

# Can a Top-Level Class Be protected?

A top-level class cannot be declared `protected`.

This is invalid:

    protected class Student {
    }

`protected` can be used for members and nested classes, but not for top-level classes.

---

# Access Modifiers on Classes

For a top-level class, the commonly relevant access levels are:

- `public`
- package-private

Example:

    public class Student {
    }

or:

    class Student {
    }

A package-private top-level class is accessible only within its package.

---

# Access Modifiers on Members

Variables, methods, and constructors can use:

- `private`
- default/package-private
- `protected`
- `public`

Example:

    class Student {

        private int id;

        String name;

        protected int age;

        public void study() {
            System.out.println("Studying");
        }
    }

Here:

    id      → private
    name    → package-private
    age     → protected
    study() → public

---

# Access Specifiers and Inheritance

Consider:

    class Parent {

        private int a = 10;
        int b = 20;
        protected int c = 30;
        public int d = 40;
    }

    class Child extends Parent {

        void show() {

            // System.out.println(a); // Not directly accessible

            System.out.println(b);
            System.out.println(c);
            System.out.println(d);
        }
    }

The child class cannot directly access the parent's private member.

It can access the appropriate package-private, protected, and public members according to Java's access rules.

---

# private and Inheritance

A common misconception is:

> "Private members are inherited by the child."

More precisely, private members are not directly accessible in the subclass.

Example:

    class Parent {

        private int x = 10;
    }

    class Child extends Parent {

        void show() {

            // System.out.println(x); // Error
        }
    }

The parent class still owns and manages its private state.

The child cannot directly access it.

---

# protected vs private

Suppose:

    class Parent {

        private int a;
        protected int b;
    }

    class Child extends Parent {

        void show() {

            // System.out.println(a); // Error

            System.out.println(b);   // Allowed
        }
    }

`private` is more restrictive than `protected`.

Use `protected` when subclasses need controlled direct access.

However, `protected` should not be used automatically. In many designs, private state with public/protected methods provides better encapsulation.

---

# default vs protected

Default/package-private access:

    class Parent {

        int value;
    }

The member is accessible within the same package.

Protected access:

    class Parent {

        protected int value;
    }

The member is accessible within the same package and also by subclasses in other packages, subject to Java's protected-access rules.

## Why are variables usually private?

Because variables represent internal state.

- Prevents direct unwanted modification

- Supports encapsulation

# Common Interview Question

## Why are methods usually public?

Not all methods are usually public.

Methods that form the class's external API are commonly public so other classes can use the object's behavior.

Internal helper methods can and should often be private.

Example:

    class Calculator {

        public int add(int a, int b) {
            return validate(a, b);
        }

        private int validate(int a, int b) {
            return a + b;
        }
    }

The important rule is:

> Make a method public only when outside code needs to call it.

# Common Interview Question

## Why should variables be private and methods public?

A common object-oriented design is:

    private data
         +
    public behavior

The data is hidden.

The behavior is exposed.

Example:

    class BankAccount {

        private double balance;

        public void deposit(double amount) {

            if (amount > 0) {
                balance += amount;
            }
        }

        public double getBalance() {
            return balance;
        }
    }

Outside code does not directly modify:

    balance

Instead, it uses:

    deposit()
    getBalance()

This allows the class to control its state.

---

# Important Correction

The statement:

> "Variables should always be private and methods should always be public."

is too absolute.

A better rule is:

> Keep fields private by default and expose only the behavior that needs to be accessible from outside.

Methods can be:

- `public` when they are part of the public API
- `private` when they are internal helper methods
- `protected` when subclass access is intentionally required
- package-private when access should be limited to the same package

# Example of Good Encapsulation

    class BankAccount {

        private double balance;

        public void deposit(double amount) {

            if (amount <= 0) {
                return;
            }

            balance += amount;
        }

        public boolean withdraw(double amount) {

            if (amount <= 0 || amount > balance) {
                return false;
            }

            balance -= amount;
            return true;
        }

        public double getBalance() {
            return balance;
        }
    }

Usage:

    BankAccount account = new BankAccount();

    account.deposit(1000);

    account.withdraw(250);

    System.out.println(account.getBalance());

Outside code interacts with the account through meaningful operations.

It does not directly manipulate:

    balance

---

# Example of Poor Encapsulation

    class BankAccount {

        public double balance;
    }

Usage:

    BankAccount account = new BankAccount();

    account.balance = -1000000;

The class has no control over its internal state.

This is generally poor encapsulation.

# Access Specifiers and Constructors

Constructors can also have access modifiers.

Example:

    class Student {

        private Student() {
        }
    }

A private constructor prevents other classes from directly creating objects using `new`.

For example:

    Student s = new Student();

would not be accessible from outside the class.

A constructor can also be:

    public Student() {
    }

or:

    protected Student() {
    }

or package-private:

    Student() {
    }

The constructor's access level controls who can create objects using that constructor.

---

# Why Use a Private Constructor?

A private constructor can be useful when object creation needs to be controlled.

Example:

    class Utility {

        private Utility() {
        }

        public static void printMessage() {
            System.out.println("Hello");
        }
    }

The class can be used without creating an object:

    Utility.printMessage();

But:

    Utility u = new Utility();

is not allowed from outside the class.

---

# Access Specifiers and static

Access modifiers and `static` solve different problems.

Example:

    class Counter {

        private static int count;

        public static int getCount() {
            return count;
        }
    }

Here:

    private

controls accessibility.

    static

controls whether the member belongs to the class rather than individual objects.

They are separate concepts.

---

# Access Specifiers and final

Similarly, `final` and access modifiers have different purposes.

Example:

    class Student {

        private final int rollNumber;
    }

Here:

    private → controls access

    final → prevents reassignment after initialization

# Real-World Example

Consider an ATM.

The ATM has internal information such as:

    accountBalance
    pin
    transactionState

Users should not directly modify:

    accountBalance

Instead, they perform operations:

    withdraw()
    deposit()
    checkBalance()

Conceptually:

    class BankAccount {

        private double balance;
        private int pin;

        public void deposit(double amount) {
            // controlled operation
        }

        public boolean withdraw(double amount) {
            // controlled operation
            return true;
        }

        public double getBalance() {
            return balance;
        }
    }

The internal state is hidden.

The required behavior is exposed.

This is encapsulation.

# Access Modifier Decision Guide

When deciding which access modifier to use, ask:

## Should only this class use it?

Use:

    private

## Should classes in the same package use it?

Use:

    default/package-private

or potentially:

    protected

depending on the design.

## Should subclasses also access it?

Consider:

    protected

But prefer stronger encapsulation when possible.

## Should any accessible external class use it?

Use:

    public

The general principle is:

> Use the narrowest access level that satisfies the requirement.

# Common Mistakes

## Mistake 1: Making every variable public

Bad:

    class Student {

        public int marks;
        public String name;
    }

Better:

    class Student {

        private int marks;
        private String name;

        public int getMarks() {
            return marks;
        }

        public void setMarks(int marks) {
            this.marks = marks;
        }

        public String getName() {
            return name;
        }

        public void setName(String name) {
            this.name = name;
        }
    }

---

## Mistake 2: Making every method public

Not every method needs to be exposed.

Bad design:

    class Order {

        public void placeOrder() {
            validate();
            calculateTotal();
            save();
        }

        public void validate() {
        }

        public void calculateTotal() {
        }

        public void save() {
        }
    }

Better:

    class Order {

        public void placeOrder() {
            validate();
            calculateTotal();
            save();
        }

        private void validate() {
        }

        private void calculateTotal() {
        }

        private void save() {
        }
    }

The public API is smaller and clearer.

This provides read-only access through the public API.

Example:

    class Student {

        private final int id;

        public Student(int id) {
            this.id = id;
        }

        public int getId() {
            return id;
        }
    }

---

## 27. Can we have a private variable with only a setter?

Yes.

This can be useful when the value should be supplied but not exposed through a getter.

---

## 28. What is encapsulation?

Encapsulation means bundling data and behavior inside a class while controlling access to the internal state.

A common implementation is:

    private fields
        +
    public methods

---

## 29. What is the relationship between encapsulation and access modifiers?

Access modifiers provide the mechanism for controlling visibility.

Encapsulation is the broader design principle of keeping internal state protected and exposing controlled behavior.

---

# Access Specifier Cheat Sheet

| Modifier | Same Class | Same Package | Subclass Different Package | Other Package |
|---|---|---|---|---|
| `private` | Yes | No | No | No |
| default | Yes | Yes | No | No |
| `protected` | Yes | Yes | Yes* | No |
| `public` | Yes | Yes | Yes | Yes |

`protected` access across packages has specific rules and is primarily available through inheritance.

---

# Most Important Rules

    private
    ↓
    Same class only

    default
    ↓
    Same package

    protected
    ↓
    Same package + subclasses

    public
    ↓
    Everywhere accessible

---

# Most Important Design Rule

Do not think:

    Variables → always private
    Methods   → always public

Think:

    Internal state
         ↓
    Keep it private when possible

    External behavior
         ↓
    Expose only what clients need

    Internal helper behavior
         ↓
    Keep it private

The general principle is:

> Use the least accessible access modifier that satisfies the requirement.

---

# Final Mental Model

    Class
      │
      ├── private fields
      │       ↓
      │   Internal state
      │
      ├── private methods
      │       ↓
      │   Internal implementation
      │
      └── public methods
              ↓
          Public API
              ↓
        Controlled behavior

Example:

    class BankAccount {

        private double balance;

        public void deposit(double amount) {

            if (amount > 0) {
                balance += amount;
            }
        }

        public double getBalance() {
            return balance;
        }

        private void internalCalculation() {
            // Internal implementation
        }
    }

The outside world sees:

    deposit()
    getBalance()

The internal implementation remains hidden:

    balance
    internalCalculation()

This is the core idea behind access control and encapsulation in Java.
